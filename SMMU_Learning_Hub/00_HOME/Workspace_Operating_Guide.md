# SMMU Learning Hub 操作方法

## 核心原则

这个知识库不追求“目录里文件很多”，而追求三件事：原始信息不丢、结论有依据、知识能被解释和应用。

本地 Markdown 是知识真相源；Linear 是进度与行动层；ChatGPT 是加工与训练层。手机无法访问本地目录时，Google Drive 只承担该时间段的临时记录，不作为自动镜像。

## 当前学习阶段与资料优先级

主资料为 `99_SOURCE\Training\MMU.pdf` 及用户提供的培训视频截图，按课程目录推进。最新培训位置、正式内容整理情况和测试记录统一以 [Current Status](Current_Status.md) 为准。

当前阶段的资料优先级：

```text
Training/MMU.pdf 与培训视频截图
        ↓ 需要架构依据时
Arm Architecture Specification
        ↓ 进入 SMMU/MMU-720AE 实现层时
MMU-720AE TRM 与 SMMUv3 Architecture Specification
        ↓
明确标注的合理推导
```

Armv9 基础阶段的主题顺序保留如下，作为后续复习底座；当前全课程顺序与正式文档见 [Current Status](Current_Status.md)：

1. MMU 的目的、虚拟地址与 VA → PA 基本模型。
2. 多级页表、地址位切分与手工 translation table walk。
3. AArch64 translation regimes、TTBR0/TTBR1、地址范围、granule 与起始级别。
4. Table/Block/Page/Fault descriptor 及上下属性字段。
5. ASID、Global/Non-global、AF、DBM、Contiguous、nT、权限与安全属性。
6. Shareability、Cacheability、MAIR/AttrIndx、Normal 与 Device memory。
7. Stage 1 translation regime 的配置：TTBR、TCR、MAIR、页表、TLBI、SCTLR。
8. MMU faults、TLB maintenance、Break-Before-Make 与映射动态修改。

## 一、从输入到掌握的五阶段闭环

### 1. Capture：先收进来

将尚未稳定的内容放进 `01_INBOX`：

- ChatGPT 问答 → `ChatGPT`
- Training/TRM 原文或截图文字 → `TRM_Clips`
- 暂时不能回答的问题 → `Questions`
- 灵感、关联猜想 → `Ideas`

Capture 阶段只要求保留上下文、来源和问题，不强迫立即分类。

### 2. Distill：按主题蒸馏

当同一主题积累了多条记录后，完成去重、查证和边界澄清，在 `02_KNOWLEDGE` 对应领域创建或更新正式知识文档。

晋升条件：

- 核心概念和职责边界已经清楚。
- 关键结论能追溯到当前主资料或其他官方规范。
- Training/TRM 事实、架构背景和合理推导已经区分。
- 能说明该概念在完整流程中的位置。
- 未解决问题明确列出，没有被结论掩盖。

原始记录继续留在 Inbox，正式知识文档通过链接引用它们。

### 3. Connect：建立关系

当内容跨越两个以上主题时，放入 `03_SYNTHESIS`：

- 完整时序或请求路径 → `End_to_End_Flows`
- 概念、接口或机制对比 → `Concept_Comparisons`
- 系统结构图 → `Architecture_Diagrams`
- 跨章节推导和设计洞察 → `Key_Insights`

形成新的主线或依赖关系时，同步更新 `Current_Status.md` 中相应的大主题和核心关系。

### 4. Explain and Test：用输出检验掌握

一个主题只有在能做到以下事情后，才可视为达到面试候选水平：

- 不看资料给出 30 秒核心解释。
- 能画出或口述端到端流程。
- 能回答“为什么需要它”“它不负责什么”。
- 能区分最容易混淆的相邻概念。
- 能处理至少两轮连续追问。

候选内容进入 `04_INTERVIEW\Candidate_Topics`；通过测试后进入 `Confirmed_Topics`。

每次测试只在 `04_INTERVIEW\Assessments` 建立一份记录，不再拆分原始问答、评估和复测清单。单份 Assessment 按以下顺序组织：

1. “检验对象”只链接对应的正式知识文档并给出测试结果，不重复培训定位、测试方式、主要范围、范围边界和反馈方式。
2. 列出资料库知识与动态追问涉及的全部知识点；知识点标题链接到本记录的详细说明，问答证据链接到对应 Q 段落。
3. 使用 🔴未掌握、🟡不稳定、⚪证据不足、🟢本轮掌握标记状态，并将需要修复的知识点排在前面。
4. 在索引后展开每一个知识点的完整内容。资料库已有内容提供正式文档链接；资料库没有的动态拓展直接补充具体知识场景和判断边界。
5. 未掌握或不稳定项必须说明：知识场景、正确因果关系、用户当前问题、错误原因和修复重点。
6. 提问前完全固定考察点、最低通过标准和高可靠答案，再检查题目是否泄露答案；看到用户回答后不得扩充评分点或改写标准答案。
7. 每个计分点都必须由题目自然、明确地引出，不设置隐藏考点。题干若已直接给出某个结论，该结论只作为背景，不再作为掌握证据。
8. 出题前先模拟“仅按题目字面作答的最短合理答案”；若该答案能够合理避开真正想考察的内容，则必须重写题目。每题只围绕一个主要能力，必要时用自然追问分层展开。
9. 若用户回答暴露的是题目设计缺陷而非知识缺口，该题标记为 `⚪题目无效 / 证据不足`，不得降低熟练度；修正题目后另行复测。
10. 面试式测试只向用户提出一个清楚的主问题，评分点作为内部检查清单，不要求用户逐条机械作答；遗漏项通过自然追问检验。
11. 面试式测试的预设高可靠答案必须写成可直接口述的连贯表达。流程图、表格和分项说明只能辅助校验或反馈，不能替代口语答案。
12. 回答后的反馈保持凝练，固定为：题目状态 → `🧭需要修正`（只写错误和不完善之处及原因，不单列正确之处）→ `📌本题要点与命中`（各要点小标题使用 ✅已扣到、🟡部分扣到、❌未扣到）→ `✅预设高可靠答案`（原样展示提问前版本）。超出原问题的知识只能标为不计分延伸。
13. 每题同时标注关联知识点编号和作答条件。自下一次测试起，每道题必须附上基于当前高可靠资料的预设答案；2026-09-11 首测作为历史记录，不追溯补写。
14. 把复测重点和通过条件保留在同一文件中，并在 `Current_Status.md` 增加测试索引。

提示后答对不视为独立通过；动态追问题只有在构成检验对象的必要边界时才影响总体等级。

### 5. Repair：修复薄弱点

单次测试中的错答、正确边界、出错原因和复测条件保留在对应 Assessment 中，不重复建立 Weakness 文件。只有同一问题跨测试持续出现，或者需要独立重学计划时，才进入 `05_WEAKNESS\Wrong_Answers`、`Knowledge_Gaps` 或 `Relearning`。

修复后回写正式知识文档，再进行测试；未通过前不提高成熟度。

## 二、目录路由决策

```text
这是原始输入吗？
  └─ 是 → 01_INBOX

这是经过查证、可复用的单主题知识吗？
  └─ 是 → 02_KNOWLEDGE/对应领域

它连接多个主题、形成比较或完整流程吗？
  └─ 是 → 03_SYNTHESIS

它用于面试表达或自测吗？
  └─ 是 → 04_INTERVIEW；单次测试记录进入 Assessments

它记录跨测试持续存在的错答、盲点或返工吗？
  └─ 是 → 05_WEAKNESS

它是原始规范或外部资料吗？
  └─ 是 → 99_SOURCE
```

## 三、ChatGPT 问答记录规则

保存位置：`01_INBOX\ChatGPT`。

命名：读取目录最大编号后加一，使用 `NN_主题.md`。不因主题归类重新编号。

默认优先写入本地 Hub。只有用户明确说明正在手机端、无法访问本地目录时，才写入 Google Drive。两者不自动同步；用户手动更新并提醒后再对齐。

为了从另一个 `SMMU` 聊天高效收录，记录时只读取最近一段完整问答，不重新读取全部历史。用户指定了具体问题时，以指定内容为准。

默认结构：

```markdown
# 标题

> 记录日期：YYYY-MM-DD
> 记录端：本地

## 问题

凝练后的原问题

## 回答

用户确认的回答正文

## 一句话总结

> 可记忆或面试表达
```

如果问题是回答规范、学习方法或工作约定，则改用 SOP/规则结构，不强套名词解释模板。

每次保存后：

1. 检查 UTF-8 编码和 Markdown 可读性。
2. 检查编号和文件名是否冲突。
3. 更新 `ChatGPT_Record_Index.md`。
4. 标注建议知识域和 Linear 主题，但不自动升格、不自动修改 Linear。
5. 检查记录日期和记录端是否存在；手机记录使用 `记录端：手机 / Google Drive`。

## 四、正式知识文档建议结构

```markdown
# 主题

## 核心结论
## 它解决什么问题
## 当前主资料明确说明
## 架构或协议背景
## 完整流程中的位置
## 易混淆点与实现边界
## 未解决问题
## 来源与相关记录
## 面试一句话
```

简单主题可以删减栏目，不为模板完整而制造空内容。

## 五、周期维护

每周或完成一个主题簇后进行一次复盘：

1. 清点 Inbox 新增内容。
2. 选择最值得蒸馏的 1–3 个主题。
3. 更新正式知识和综合材料。
4. 用追问或模拟面试验证成熟度，并形成单份 Assessment。
5. 只有问题跨测试持续存在时，才晋升到 Weakness。
6. 更新 Current Status 中的培训、整理和测试进度；只有用户明确要求时才更新 Linear Next Actions。

同时在学主题最多保持 3 个，避免所有 Linear Issue 都长期停留在“进行中”。
