# SVA：共享虚拟地址与进程—设备绑定

> 本条按手机端 Inbox 方式记录：保留核心问题、机制关系、完整流程与面试式总结，后续可再并入 `04_地址转换流程` / `05_软件编程模型`。

## 原问题 1：SVA 到底解决什么问题？

### 核心结论

**SVA（Shared Virtual Addressing）的本质不是一种新的地址翻译算法，而是把 Device 接入某个 Process 的虚拟地址空间，让 Device 在代表该进程工作时可以直接使用该进程的 VA。**

传统 DMA 通常是：

```text
Application VA
    ↓
CPU Page Table
    ↓
PA

Device 侧另外建立：
IOVA
    ↓
SMMU Page Table
    ↓
PA
```

CPU 和 Device 看到的地址不同：

```text
CPU    → VA
Device → IOVA
```

SVA 希望做到：

```text
Application ptr = VA
      │
      ├── CPU 直接使用该 VA
      │
      └── Device 也直接使用该 VA
```

因此 SVA 的核心价值是：

> **CPU 和 Device 共享 Process Virtual Address Space，而不是额外维护一套独立的 Device IOVA 语义。**

## 原问题 2：一个 Device 同时服务多个进程时，SMMU 怎么知道 VA 属于哪个进程？

仅有 VA 不够，因为不同进程可以有相同 VA：

```text
Process A:
VA 0x4000 → PA_A

Process B:
VA 0x4000 → PA_B
```

所以 Device transaction 必须携带“进程身份”。

PCIe 侧通常使用：

```text
PASID = Process Address Space ID
```

进入 SMMUv3 后，对应：

```text
SSID = SubstreamID
```

最终 transaction 可以理解成：

```text
StreamID = 哪个 Device / Stream
SSID     = 这个 Device 当前代表哪个 Process
Address  = 该 Process 的 VA
```

一句话：

> **SID 找 Device，SSID 找 Process。**

---

## SVA 中 StreamID、SSID、STE、CD 的关系

```text
Device transaction
      │
      ├─ StreamID
      │     ↓
      │    STE
      │     ↓
      │  Stream级配置 / Stage2配置 / CD表入口
      │
      └─ SSID / PASID
            ↓
           CD
            ↓
      ASID + TTBR + Stage1配置
            ↓
      Process Page Table
```

因此，一个 Device 可以通过多个 SSID 同时代表多个进程：

```text
SID = 20, SSID = 10 → Process A
SID = 20, SSID = 11 → Process B
```

这就是 SMMUv3 Substream 对 SVA 的核心价值。

---

## Context Descriptor 为什么是关键

Context Descriptor（CD）保存 Stage 1 translation context，概念上包括：

```text
CD
├─ ASID
├─ TTBR / Page Table Base
├─ Stage1 translation controls
└─ 其他地址翻译属性
```

因此 SVA bind 后，某个 SSID 会对应某个进程的 CD：

```text
Process A
├─ ASID_A
├─ Page Table_A
└─ PASID/SSID_A
        │
        │ SVA Bind
        ▼
CD[SSID_A]
├─ ASID = ASID_A
└─ TTBR → Page Table_A
```

CPU 与 SMMU 可以这样对照：

```text
CPU Stage1
TTBR0_EL1
├─ ASID
└─ Page Table Base

SMMU SVA Stage1
SSID
 ↓
CD
├─ ASID
└─ TTBR
```

所以：

> **SVA 真正实现共享地址空间的关键，是让 SMMU 的 CD 指向该 Process 的 Stage 1 page table context。**

---

## SVA Bind 是什么

SVA Bind 本质上是建立：

```text
Device + Process
```

之间的绑定关系。

典型逻辑：

```text
Process A
mm_struct
├─ pgd / page table root
├─ ASID
└─ PASID
      │
      │ SVA Bind
      ▼
SMMU
STE[Device SID]
      ↓
CD[Process SSID]
├─ ASID_A
└─ TTBR → Process A Page Table
```

绑定完成后 Device 发：

```text
SID  = Device
SSID = Process A
VA   = 0x4000
```

SMMU 就可以：

```text
SID  → STE
SSID → CD
CD   → ASID + TTBR
VA   → Process A Page Table
     → PA
```

## 原问题 3：SVA 是不是“让 Process 关联 Device，从而控制 Device 的读写”？

### 更准确的说法

可以这样理解，但不要说成“Process 控制 Device”。

更准确的是：

> **SVA 建立 Device 与 Process Address Space 的绑定，使 Device 在代表该 Process 访问内存时，受到该 Process 页表 mapping 和 permission 的约束。**

例如 Process A 页表：

```text
VA 0x1000 → RW
VA 0x2000 → RO
VA 0x3000 → Invalid
```

Device 用 Process A 的 SSID 访问：

```text
Write 0x1000 → 允许
Write 0x2000 → Permission Fault
Access 0x3000 → Translation/Page Fault
```

所以：

```text
Process Page Table
        ↓
定义这个 Process 能访问什么、以什么权限访问
        ↓
SVA 让 Device 复用这套地址空间语义
        ↓
SMMU 执行 translation + permission check
```

一句话：

> **SVA 不是“进程控制设备”，而是“设备代表进程访问内存”。**

## SVA 为什么经常和 ATS 一起出现

SVA 解决的是：

```text
Device 使用哪个 Process Address Space
```

ATS 解决的是：

```text
Device 如何高效获得该 VA 的 translation result
```

典型流程：

```text
Device
  │ VA + PASID
  ▼
ATS Translation Request
  ↓
Root Complex
  ↓
SMMU
  │ SID → STE
  │ SSID → CD
  │ CD → Process Page Table
  ↓
Translation Result
  ↓
ATS Completion
  ↓
Device ATC Cache
  ↓
后续 Pre-translated Transaction
```

所以：

> **SVA 决定“共享谁的地址空间”，ATS 负责“高效查询这个地址空间的 translation”。**

---

## SVA 为什么又经常需要 PRI

用户进程的页面可能暂时不在内存：

```text
Process VA
   ↓
PTE = Not Present
```

CPU 访问时有 CPU Page Fault；Device 使用 SVA 访问时则需要 Device-side page fault recovery。

支持 ATS + PRI 时：

```text
Device ATS Request
      ↓
Translation Failure: Page Not Present
      ↓
PRI Request
      ↓
SMMU PRIQ
      ↓
IO Page Handler / OS
      ↓
更新 Process Page Table
      ↓
CMD_PRI_RESP
      ↓
Device ATS Retry
      ↓
Translation Success
```

所以可以记成：

```text
SVA → Device 使用 Process VA
ATS → Device 查询 VA 怎么翻
PRI → VA 缺页时让 OS 把 page 准备好
```

---

## SVA 与 Stage 2 的关系

SVA 并不排斥虚拟化下的 Stage 2：

```text
Process VA
   ↓ Stage 1（CD / ASID / TTBR）
IPA
   ↓ Stage 2（STE / VMID / S2TTB）
PA
```

其中：

```text
Stage 1
→ Process address space
→ 每个 SSID 可以有自己的 CD

Stage 2
→ VM / Host isolation
→ 同一个 Stream 的多个 Substream 可以共享 Stage2配置
```

所以一个完整的 SVA transaction 可以同时携带：

```text
SID + SSID + VA
```

并经历：

```text
SID  → STE → Stage2 context
SSID → CD  → Stage1 context
VA   → S1 → IPA → S2 → PA
```

---

## SVA 的系统价值

传统 DMA：

```text
Application pointer
   ↓
Driver重新建立 DMA mapping
   ↓
Device使用独立 DMA address
```

SVA：

```text
Application pointer / VA
   ↓
Device直接使用
```

主要价值：

- 减少额外 DMA address mapping 和 pointer translation。
- 方便 GPU / AI accelerator / NIC 等设备直接访问复杂用户态数据结构。
- Device 可以和 CPU 共享同一个 Process virtual-memory view。
- 配合 ATS/PRI 后，可以进一步支持高性能 translation cache 和 demand paging。

---

## 安全边界

SVA 并不意味着 Device 可以访问任意 Process。

系统软件仍然必须控制：

```text
PASID / SSID allocation
SVA Bind / Unbind
CD creation
Device PASID enable
Page Table lifetime
TLBI / ATC invalidation
Process exit / mm_notifier
Stage2 isolation（虚拟化场景）
```

因此 Device 只能使用软件为它合法建立的 Process Context。

## 完整模型

```text
                 Process / Application
                 mm_struct
                 ├─ ASID
                 ├─ PASID
                 └─ Page Tables
                        ▲
                        │ SVA Bind
                        │
PCIe Device             ▼
+-------------+      SMMU
| StreamID    | ───→ STE
| PASID/SSID  | ───→ CD
| Process VA  |      ├─ ASID
+-------------+      └─ TTBR ─────────→ Process Page Table
                           │
                           ▼
                       VA → PA
```

如果再加入高性能与缺页恢复：

```text
ATS → Device缓存translation到ATC
PRI → Device缺页时请求OS补page
```

## 面试式总结

> **SVA 让 Device 直接使用某个 Process 的虚拟地址空间。StreamID 标识 Device/Stream，PASID/SSID 标识 Device 当前代表的 Process；SMMU 通过 SID 找 STE、通过 SSID 找 CD，CD 中保存该 Process 的 ASID、TTBR 等 Stage 1 translation context，从而使用 Process page table 对 Device 发出的 VA 做 translation 和 permission check。SVA 经常与 ATS、PRI 配合：ATS 用于加速 translation，PRI 用于处理 Device 访问进程 VA 时产生的 demand paging。**

### 一句话记忆

> **SVA = Device 直接使用 Process VA；SID 找设备，SSID 找进程，CD 找页表，ATS 加速翻译，PRI 处理缺页。**
